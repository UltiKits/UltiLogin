# UltiLogin — UAT Checklist

This document is the executable companion to `FEATURES.md`: one row per feature stating the
steps to exercise it and the observable truth that proves it works. It is an internal reference
for real-machine verification, not user-facing documentation.

> Batches are dispatched at 60 rows or fewer, and a batch never spans two repositories. There are
> exactly two legitimate exits to `human-uat-pending`: a row needing the pixel layer while the
> real-client harness is not ready, and a row needing personal credentials. Every other row must
> reach `pass`, `fail`, or `blocked`.

## Conventions

- **Columns:** `ID`, `Preconditions`, `Steps`, `Expected`, `Layer`, `Covers`.
- **ID:** cites its `FEATURES.md` ID verbatim. A negative case suffixes the checklist ID only,
  as `.neg-<slug>` — a negative case still tests the same feature, so the base ID is unchanged.
- **Layer**, copied verbatim from the real-client acceptance tooling's fixed vocabulary so no
  translation step exists at dispatch time: `protocol`, `java-client`, `os-input`, `pixel`,
  `server`, `human`.
- **Delegated-authorization UltiCloud rows:** a row whose
  Steps can only be exercised through an authenticated UltiCloud panel session carries the fixed
  Preconditions phrase `an authorized UltiCloud session under the maintainer's delegated
  authorization` (appended to, not replacing, the row's own preconditions) and Layer `server`.
  This module's `/panel` command is such a row: it hands the player a real UltiCloud link,
  which the maintainer's delegated authorization lets the acceptance tester complete
  directly, scoped to the backend staging stack only.
- **Mailpit-sink rows (this module's own addition to the authenticated-session pattern):** a
  row whose Steps can only be exercised by actually sending an email and reading the
  resulting code from a real inbox carries the fixed Preconditions phrase `an SMTP server
  reachable from the shared server with an inbox the executor can read` and Layer `server`. The
  shared server's `config.yml` `email.*` block points at a local Mailpit sink
  (no personal mail credentials involved, nothing leaves the machine), so these rows are
  executable and observed through the running server. Every row under `## Email Binding` and
  `## Password Recovery` that causes a real verification email to be sent is such a row. A
  negative row that only needs a *pending* request to already exist (not the real received code)
  still carries this phrase and Layer, because creating that pending state itself required a real
  send — see `ultilogin.email.verify.neg-wrong-code` for the one row where this distinction
  matters.
- **Expected** must name an observable truth — an exact chat line, a log line, a database row,
  an inventory slot — and never the words "it works".
- **Covers** back-references a GUI class excluded from the JaCoCo coverage gate; left blank when no such class
  applies.
- A row whose Preconditions name a prior row must appear after that row in file order — asserted
  mechanically: for every row, every checklist ID cited in its Preconditions cell must have a
  strictly smaller line number in this file than the row citing it.
- **Config-per-file rule:** one checklist row per `@ConfigEntity`-annotated class, never
  one row per key. The row's ID is suffixed `-yml` (`ultilogin.config.login-yml`,
  `ultilogin.config.email-yml`), aggregating every per-key `ultilogin.config.<file-stem>.*` row
  for that file rather than citing a single one of them.
- **One message source:** every line this module shows or logs comes from its language file
  (`lang/en.json`, `lang/zh.json`), so it follows the framework's `language` setting
  (UltiKits/UltiLogin#20). The three `gui-mode.title-*` settings and the twenty-one `messages.*`
  settings of `login.yml` are written into the file in the server's language while they are still
  built-in text, and the module sends exactly what the file holds (`ultilogin.lifecycle.legacy-text-defaults`).
  Every row whose Expected quotes text therefore carries `language: en` and quotes `lang/en.json`'s text
  with its colour codes left out, and assumes those settings hold the text this build writes under
  `language: en` unless its own Preconditions set one.
- **Airborne-rejoin scenario ID:** `ultilogin.protection.movement-block.airborne-rejoin` exercises the existing
  `FEATURES.md` feature `ultilogin.protection.movement-block`; it is a scenario suffix, not a separate feature.
- **Config text rows:** `ultilogin.config.login.materialize-fresh` and `ultilogin.config.login.materialize-switch`
  exercise `FEATURES.md`'s `ultilogin.lifecycle.legacy-text-defaults` on a fresh file and across a `language`
  switch; they are named by the config-text naming convention (`<prefix>.config.<file stem>.materialize-*`)
  rather than by that ID, and the upgrade case keeps the existing row `ultilogin.lifecycle.legacy-text-defaults`.
- **Web-flow and stub rows (`/panel` end to end).** The rows of `## Panel` from `ultilogin.panel.open` on (except
  `ultilogin.panel.open.neg-disabled`, `ultilogin.panel.help`, the `ultilogin.setpassword*` rows, `ultilogin.login.neg-empty-hash` and
  `ultilogin.panel.state.logged-out-unbound-register.neg-ip-limit`, which need no UltiCloud) name one of two environments in their
  Preconditions, and a row never mixes the two:
  - `Environment: backend staging (web-flow setup)` — the real gateway and panel of the backend staging stack
    (`api-staging.ultikits.com`), a Paper server running the UltiTools-API 6.3.1 candidate jar and this build, and a
    browser. The row carries the fixed phrase `an authorized UltiCloud session under the maintainer's delegated
    authorization`. Web-flow setup, assumed unless the row says otherwise: `language: en` in UltiTools' own `config.yml`;
    in `login.yml`, `ulticloud.enabled: true` and `session-enabled: false` (a player who rejoins is not logged in by a
    session), applied with `/ul reload UltiLogin`; the server signed in to UltiCloud with `ulticloud login` from the
    console, completed in the browser as the owner account `O`; the panel shown in English. Accounts `A` and `B` are two
    further UltiKits accounts the run creates in the panel's sign-up page with throwaway names and passwords before the
    first row that needs them.
  - `Environment: stub (stub setup)` — the same server and build, but its UltiCloud connection points at a local stub
    gateway that the UAT run starts itself, as the framework's player-link rows do: it speaks protocol 2, answers `hello`
    with `welcome`, answers each `player.link.create` with the frame the row names (`player.link.created` with a
    `url`, an `expiresAt` and `acceptedProofs`, or an error such as `rate_limited` or `link_not_permitted`), sends
    `player.link.completed` and `player.link.expired` with the `replyTo` of the create they belong to, and records every
    frame the server sends (the `player.link.completed.result` above all). There is no browser. A stub row's Expected
    quotes only the game's chat and console, the account data `logadmin info` shows, and the stub's recorded frames.
  - Game players are client names the tester controls, written as letters and digits (`W`, `L1`, ...); "has never joined
    this server" means no UltiLogin account and no link exists for the name. A "fresh browser" is a private window with no
    panel session; "a browser signed in as A" is one where A logged in on the panel's own login page. `<S>` is the server
    name the page shows. Nothing polls: the outcome reaches the game within a few seconds of the browser action or the
    stub frame, so in-game lines are read within 10 seconds of it.
  - **Page texts** are quoted from the English text of the panel frontend (`UltiKits/UltiPanelFrontend`, branch
    `feature/ulticloud-v2` at commit `f602d36`, files `src/locales/en/auth.ts` and `src/locales/en/account.ts`), with the
    page's `{name}`, `{server}` and `{owner}` filled in. That commit is the newest on the branch and is **not yet
    confirmed to be what the backend staging stack serves**: the first staging run (plan 01-05) confirms each page
    literal or amends it. A page literal that differs on staging is recorded as that clause failing (`blocked` when the
    page belongs to another build, with the page text noted); the row's game-side clauses are judged on their own.
  - **IDs.** These rows are named by scenario (`ultilogin.panel.state.<page state>`, `ultilogin.panel.link.<outcome>`,
    `ultilogin.panel.unlink.<account kind>`, ...), not as `<FEATURES ID>[.neg-<slug>]`, except those that carry the ID
    of a `FEATURES.md` row. The scenario rows exercise `FEATURES.md`'s `ultilogin.panel.open`,
    `ultilogin.panel.completion` and `ultilogin.panel.expiry`; in addition the two
    `ultilogin.panel.state.logged-out-unbound-register*` rows exercise `ultilogin.panel.web-registration`,
    `ultilogin.panel.timeout-pause` the row of the same ID, `ultilogin.login.neg-empty-hash` `ultilogin.login.authenticate`,
    and `ultilogin.setpassword` and `ultilogin.setpassword.neg-has-password` `ultilogin.setpassword.set`. The two unlink
    rows exercise the panel's own unlink, which has no source in this repository, and check its effect on `/panel`. The
    rows of `## Release metadata` check this module's `plugin.yml` declarations, which the framework reads and
    `PluginMetadataTest` pins; `FEATURES.md` catalogues runtime behaviour and has no row for them.
- This module ships `login-timeout: 60`, `security.max-login-attempts: 5`,
  `security.lockout-duration: 900`, `security.lockout-type: BOTH`, `max-register-per-ip: 0` (no per-IP limit), `password.min-length: 6`,
  `password.max-length: 32`, `gui-mode.enabled: false` (command-mode password flow) as its
  defaults; every row below assumes these unless its own Preconditions say otherwise.
- **Lockout scenarios:** the address-isolation, address-spray and IP-success scenario rows explicitly use
  `security.max-login-attempts: 3`, `security.lockout-duration: 600`, `login-timeout: 600`,
  `session-enabled: false`, `gui-mode.enabled: false` and `max-register-per-ip: 0`. Their registered test accounts
  have known, nonempty throwaway game passwords. Restart before applying these values with `/ul reload UltiLogin`,
  clearing all earlier in-memory failures/locks, and permit no other wrong-password attempts during the scenario.
  Run the numbered authentication steps within 60 seconds (well inside both 600-second windows); retain their
  timestamps. `language: en`, this build's catalogue loaded by that reload and this build's English `messages.*`
  values apply. Record the previous non-security settings, then restore them and the security shipped defaults
  (`max-login-attempts: 5`, `lockout-duration: 900`, `lockout-type: BOTH`) and restart after each scenario.
  A source-bound client must actually appear at the specified address in the server's join log; retain those
  lines. If the client/proxy cannot expose two different observed addresses, the cross-address row is `blocked`,
  never passed by changing a player name or by substituting a different account.
- **Lockout scenario IDs:** the five `ultilogin.config.login.security.lockout-type.*` scenario IDs added for pair
  isolation, address spraying, success-reset, fresh defaults and value preservation all exercise the existing
  `FEATURES.md` lockout-type feature; they are scenario suffixes, not additional configuration keys.
- **Console lines carry the module-logger prefix.** Every line this module logs reaches the console as
  `[UltiTools] [UltiLogin] <text>`: Paper adds `[UltiTools] `, and the framework's module logger (`PluginLogger`)
  adds `[UltiLogin] ` (this module's `plugin.yml` `name`). A console line quoted below is the `<text>` after both
  prefixes, character for character, unless the row quotes a prefix itself; a row that counts or excludes this
  module's console lines means lines carrying `[UltiLogin]`. A line the framework logs is quoted after Paper's
  prefix, with its own `[UltiTools-API] ` where the row shows it.
- **Panel button labels are compared as text, not as rendered case.** Where a web-flow row quotes a button of the panel
  (for example "Create new account", "Confirm and link", "Sign in", "Cancel"), the quoted words are the button's
  text. The panel's button style may render them in capitals (a CSS text transform; the page's own text holds the
  quoted case), so a row passes on the quoted words whatever case the button is drawn in (Phase 19 production smoke,
  B32).
